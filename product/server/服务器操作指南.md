## 2. 登录与日常巡检

在本机 PowerShell 中登录：

```powershell
ssh dsh-server
```

该别名依赖本机已有 SSH 配置和专用部署密钥。以下 Bash 命令均在服务器的 root 终端执行。

```bash
cd /www/wwwroot/117.72.10.87/26-009DSHlink
batona-deploy --status
systemctl is-active batona-gateway frps nginx
curl -fsS --max-time 5 http://127.0.0.1:3090/healthz
curl -kfsS --max-time 5 https://117.72.10.87/healthz
ss -ltnp | grep -E ':(80|443|7000|7500|3080|3081|3082|3090)\b'
```

预期结果：

- 当前 frps 模式下，三个服务均为 `active`；以后切换内置隧道后，frps 停用属于正常情况。
- `/healthz` 返回 `ok: true`，线上版本与部署目标一致。
- 网关监听 `127.0.0.1:3090`；3080、3081、3082 若存在监听，必须只在回环地址。
- `batona-deploy --status` 中的服务、版本和堆上限检查正常。仍需结合端口检查，不能把 frps 通配监听的提示当作允许公网开放。

`-k` 仅用于诊断时跳过证书校验，不能证明客户端已信任证书。健康检查也不代表 PC 在线或真实会话已经可用。

如果提示找不到 `batona-deploy`，可在上述仓库目录使用等价入口：

```bash
bash product/server/deploy.sh --status
```

## 3. 更新与回滚网关

### 日常更新

先确保目标代码已经提交、推送，服务器工作树没有待保留的本地修改：

```bash
cd /www/wwwroot/117.72.10.87/26-009DSHlink
git status --short
batona-deploy --status
batona-deploy
batona-deploy --status
```

`batona-deploy` 会拉取并快进到 `origin/main`，调用同一提交的安装脚本构建网关，再核对服务、健康接口版本和 systemd 堆上限。更新会重启网关，应安排在允许短暂断线的时间执行。

不要提前手工 `git pull`，也不要把 `install.sh --update` 作为日常更新入口。配置和持久数据会保留，正常更新后 PC 和手机无需重新绑定。

### 指定版本或回滚

```bash
# 将占位内容替换为实际存在的 tag 或 commit
batona-deploy --tag <tag-or-commit>

# 回退到部署状态文件中记录的 previousCommit
batona-deploy --rollback
batona-deploy --status
```

部署状态记录在 `/var/lib/batona-gateway/.deploy-state`。部署失败时脚本会尝试使用已记录的回滚点恢复；没有回滚点或恢复失败时，需要人工排查。不要只凭脚本的回滚提示判断恢复成功，应再次检查健康接口和客户端连接。

代码回滚不恢复 Nginx、首页、认证数据或隧道模式。指定版本及回滚后可能处于 detached HEAD；下次普通 `batona-deploy` 会重新部署所跟踪分支。

### 发布前的本地验证

在本机 `product/server/gateway` 目录执行：

```bash
npm run typecheck
npm run build
npm run smoke
npm run tunnel-protocol
npm run tunnel
```

这些直接运行 TypeScript 的测试需要适合原生 TS 执行的 Node 版本（网关 README 指定 Node 24+）；生产构建产物基线为 Node 18+。修改隧道协议时，还需运行 PC 端对应黄金向量测试。发布前递增网关版本并同步 lock 文件；真实 DSH 探针会调用模型，不属于常规巡检。

## 4. 查看日志与重启

```bash
# 最近的网关与隧道日志
journalctl -u batona-gateway -n 100 --no-pager
journalctl -u frps -n 50 --no-pager

# 持续观察网关日志，按 Ctrl+C 退出
journalctl -u batona-gateway -f

# 查看启动配置，核对 --max-old-space-size=512
systemctl cat batona-gateway
```

需要重启网关时：

```bash
systemctl restart batona-gateway
systemctl is-active batona-gateway
curl -fsS --max-time 5 http://127.0.0.1:3090/healthz
```

重启会中断现有连接；随后确认 PC 隧道重连、手机恢复连接。frps 模式下排查隧道故障时可单独执行 `systemctl restart frps`，也会造成连接中断。

## 5. 配置、数据与备份位置

| 路径 | 用途 |
| --- | --- |
| `/opt/batona-gateway/app` | 部署后的运行应用，入口 `dist/app.mjs` |
| `/etc/batona-gateway/config.json` | 网关配置、适配器、共享密钥及隧道开关 |
| `/etc/batona-gateway/server-info.json` | 服务器绑定资料，权限应为 `600` |
| `/var/lib/batona-gateway` | 用户、设备及其他持久数据 |
| `/var/lib/batona-gateway/.deploy-state` | 部署与回滚记录 |
| `/etc/frp/frps.toml` | frps 配置，`proxyBindAddr` 必须为 `127.0.0.1` |
| `/etc/systemd/system/batona-gateway.service` | 网关启动与内存限制 |
| `/www/server/panel/vhost/nginx/117.72.10.87.conf` | 宝塔主虚拟主机 |
| `/www/server/panel/vhost/nginx/proxy/117.72.10.87/batona-gateway.conf` | DSH 接口分流配置 |
| `/www/wwwroot/117.72.10.87/00-001WebMainIndex` | 首页静态文件 |

修改配置前将相关文件备份到 root 专用目录。例如，修改网关配置前执行：

```bash
umask 077
backup_dir="/var/backups/batona-gateway/$(date +%Y%m%d-%H%M%S)"
mkdir -p "$backup_dir"
cp -a /etc/batona-gateway "$backup_dir/"
cp -a /etc/frp "$backup_dir/"
cp -a /etc/systemd/system/batona-gateway.service "$backup_dir/"
```

该示例仅备份配置。需要备份认证数据时，应在维护窗口停止网关后复制 `/var/lib/batona-gateway`，完成后启动并核验；首页和 Nginx 配置应另行备份。备份可能包含凭据，不放入网站目录或 Git。不要通过删除配置、认证数据来解决普通连接故障。

## 6. 首页与 Nginx 维护

首页源码在本机 `D:\_Projects\00-001WebMainIndex`，服务器静态目录见上表。DSH 网关与首页共用 HTTPS 入口，路径分工如下：

| 路径 | 行为 |
| --- | --- |
| `/` 及静态资源 | 由 WebMainIndex 提供 |
| `/api/`、`/ws`、`/tunnel`、`/healthz` | 保持原路径转发至 `127.0.0.1:3090` |
| `/remote/` | 旧浏览器客户端 |
| `/pair.html` | 返回 404 |
| HTTP 80 | 重定向至 HTTPS |

修改反代时以 [nginx-batona-gateway-routes.conf](nginx-batona-gateway-routes.conf) 为准，保留 WebSocket 的 `Upgrade`、`Connection` 头及长连接超时。不要用全站 `location /` 反代覆盖首页，也不要覆盖其他项目已有的路由。

配置修改后，语法检查通过才平滑重载：

```bash
nginx -t && systemctl reload nginx
curl -kIsS https://117.72.10.87/
curl -kfsS https://117.72.10.87/healthz
curl -kIsS https://117.72.10.87/remote/
curl -kIsS https://117.72.10.87/pair.html
curl -IsS http://117.72.10.87/
```

还需检查首页依赖资源，以及真实 PC/手机的 WebSocket 连接。普通 HTTP 请求 `/tunnel` 返回 426 表示需要升级到 WebSocket，不等于隧道故障。

2026-09-22 首页切换前的备份位于 `/var/backups/dsh-homepage/20260922-134152/`，包含旧 DSH include 和 `index.html`、`scripts/index.js`、`data/updates.json`。这是历史备份，使用前确认内容是否符合本次恢复目标；日常修改仍需建立新备份。恢复路由后也必须先 `nginx -t` 再重载。

## 7. 隧道模式与端口

| 端口 | 用途 | 公网规则 |
| --- | --- | --- |
| 443 | HTTPS、WSS、内置隧道 | 放行 |
| 80 | HTTP 跳转及需要时的证书验证 | 按现有站点用途保留 |
| 7000 | frps 客户端接入 | 当前兼容模式必须放行 |
| 3080 / 3081 / 3082 | DSH / 目录服务 / Codex 桥 | 仅回环，不对公网放行 |
| 3090 | 网关内部 HTTP | 仅回环，不对公网放行 |
| 7500 | frps 管理端口 | 不对公网放行 |

SSH 管理入口沿用现有配置和访问规则。云安全组与服务器防火墙都需要匹配上述端口边界。

查看当前隧道模式：

```bash
cd /www/wwwroot/117.72.10.87/26-009DSHlink
bash product/server/install.sh --tunnel status
```

仅在全部 PC 客户端已支持内置隧道、Nginx 已正确转发 `/tunnel` 后切换：

```bash
bash product/server/install.sh --tunnel on
bash product/server/install.sh --tunnel status
batona-deploy --status
```

启用操作会停用 frps 并重启网关。确认所有 PC 经 443 重连成功后，才关闭公网 7000。

需要恢复 frps 时，先恢复云安全组与防火墙的 7000 入口，再执行：

```bash
bash product/server/install.sh --tunnel off
bash product/server/install.sh --tunnel status
batona-deploy --status
```

Codex 的服务器适配器只能通过 `http://127.0.0.1:3082` 访问 PC 桥。是否启用应以实际配置和 PC 能力核验为准，不能为了接通而将 3082 开放到公网。

## 8. 绑定电脑与手机

只在 root 的受控终端需要导出绑定资料时执行：

```bash
cd /www/wwwroot/117.72.10.87/26-009DSHlink
bash product/server/install.sh --show-binding
```

输出含完整凭据，不复制到日志、工单、仓库或公开截图。日常巡检、安装和更新不需要导出连接串。

绑定顺序：

1. PC 导入服务器连接串，启动本地 DSH 和隧道。
2. 手机扫描 PC 展示的二维码或导入同一连接串。
3. 手机使用网关账号并按登录提示完成 TOTP 绑定和验证。
4. 确认能读取工作区和会话，再验证消息、审批及提问往返。

PC 会自动上报随 DSH 进程变化的 launch token。DSH 重启后不要继续使用旧 token。设备丢失时，通过客户端设备管理吊销对应设备。

## 9. 常见故障排查

| 现象 | 排查顺序 |
| --- | --- |
| 首页能打开，手机无法连接 | 检查 `/healthz` → Nginx `/api/`、`/ws` 路由和升级头 → PC 隧道及本地后端状态 |
| 本机 3090 健康，HTTPS 失败 | 检查 Nginx 状态、配置语法、反代、证书和 443 访问规则 |
| 网关正常，但 DSH 不可用 | 检查 PC 是否在线、DSH 是否启动、隧道是否连接、launch token 是否重新上报 |
| Codex 不可用 | 核对 PC 桥与 App Server 能力、服务器适配器配置和回环 3082；模型与工具仍由 PC 提供 |
| `git fetch` 失败 | 检查服务器到 Gitee 的网络、只读部署公钥及 SSH 配置；不替换为个人可写私钥 |
| 部署提示工作区有修改或无法快进 | 先 `git status --short`、`git diff` 确认是否有需保留的热修；不要直接强制覆盖 |
| `npm ci` 失败 | 在本机检查并同步 `package.json` 与 lock 文件，提交后重新部署 |
| 线上版本与目标不一致 | 查看部署输出及回滚记录，确认构建与重启是否成功，再运行 `batona-deploy --status` |
| 拉取历史时内存异常 | 检查网关日志、历史事件聚合限制及 systemd 的 `--max-old-space-size=512` |
| 首页被网关登录页覆盖 | 检查是否误启用全站反代，恢复首页与接口分流 |
| `/Easyplay/`、`/RateConverter/` 返回 502 | 最近记录中两者在首页切换前后均为 502，需单独检查各自上游 |

## 10. 新服务器初始化参考

现有服务器已部署，无需再次执行首次安装。新机器需要 root、Git、curl、systemd，以及指向 Gitee 私有仓库的专用只读部署公钥；先验证 `ssh -T git@gitee.com` 的认证结果，再检出代码。

```bash
git clone --filter=blob:none --no-checkout \
  git@gitee.com:li-jinhang7/26-010-dshplugin.git \
  /www/wwwroot/117.72.10.87/26-009DSHlink
cd /www/wwwroot/117.72.10.87/26-009DSHlink
git sparse-checkout init --cone
git sparse-checkout set product/server
git checkout main
bash product/server/deploy.sh --status

# 替换为新服务器 IP；不传 --password 时，脚本为新安装生成随机密码
bash product/server/install.sh --install --ip <公网IP> --admin admin
```

新机器可按实际情况调整目录，但后续包装命令必须指向同一工作树。创建便利命令（普通脚本，不是软链接）：

```bash
cat > /usr/local/bin/batona-deploy <<'EOF'
#!/usr/bin/env bash
exec bash /www/wwwroot/117.72.10.87/26-009DSHlink/product/server/deploy.sh "$@"
EOF
chmod 755 /usr/local/bin/batona-deploy
```

首次安装还需要配置首页、Nginx HTTPS 入口和防火墙。安装脚本提供 `--selfsigned <公网IP>` 生成含 IP SAN 的自签证书，使用时客户端需显式信任；安装脚本不会替代完整的 HTTPS 站点配置。完成后按本文巡检，再验证 PC、手机真实连接。
