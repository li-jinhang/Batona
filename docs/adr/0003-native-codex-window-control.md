# ADR 0003：以原生 Codex 窗口作为同一任务的唯一写入面

状态：已接受（2026-09-22）

## 背景

用户需要继续使用 Windows 上的 Codex 原生应用，并从 Batona Android 操作同一任务。ChatGPT/Codex 官方手机端不能替代 Batona。当前 Batona PC 另起一个 stdio `app-server`：它可以只读发现原生任务，但对原生应用已经加载的任务调用 `thread/resume` 会触发活动写入者冲突。复制、分叉或轮流抢占任务都会破坏“手机发送等同于电脑端发送”和双向实时同步。

Codex 的公开协议允许客户端连接自己启动的 `app-server`，但没有公开接口让 Batona 加入 Codex Desktop 已经持有的私有 stdio 连接。系统必须在这个边界内保持单一任务权威源。

## 决定

Windows Codex 原生应用是原生任务的唯一运行时所有者和写入面。Batona 不再通过第二个 `app-server` 向这类任务调用 `thread/resume`、`turn/start`、`turn/steer`、`turn/interrupt` 或交互响应接口。

Batona PC 增加“原生界面代理”通道。历史记录继续由只读 `app-server` 提供；任务运行期间，PC 通过 Windows UI Automation 观察经过验证的 Codex 原生窗口，把新请求、可见的思考摘要、流式回复、工具状态、审批和提问归一化为增量事件后转发给手机。任务结束后再用 `thread/read` 或 `thread/turns/list` 的持久记录校正临时增量。

手机提交消息、切换模型或处理交互时，PC 通过可访问性控件定位并操作原生 Codex 界面。实际提交动作发生在原生 Codex 输入框；模型选择、审批和提问同样由原生界面完成，因此桌面与手机操作属于同一个任务、同一个写入者。坐标点击和持续视频流不作为正常路径；只有控件无法结构化表达时，才可按需返回受限的窗口局部快照辅助用户确认。

独立 `app-server` 保留为只读镜像，用于任务列表、状态和持久历史读取。它不得把“可读取”解释为“可写入”。Batona Android 用结构化历史和增量事件维持手机聊天界面，无需持续传输桌面视频。官方协议将来若提供 Desktop 共享控制端点，可用它替换原生界面代理而不改变手机侧的任务身份。

原生窗口控制遵循以下边界：

- 仅允许配对设备控制已验证签名、包身份、进程和窗口句柄的 Codex 控件，不提供任意桌面或其他应用控制。
- 增量事件与输入经现有认证和加密链路转发；服务器不持久化可访问性树、窗口快照、按键、剪贴板或任务正文。
- PC 锁屏、UAC 安全桌面、Codex 窗口缺失、任务身份无法确认或控制链路断开时拒绝输入；手机保留草稿并显示明确状态。
- PC 显示远程控制正在进行的本地提示；同一时刻只允许一个已配对手机控制输入，电脑本地输入始终可接管。
- ChatGPT/Codex 官方手机端不属于产品依赖，也不作为 Batona 的回退路径。

## 验收

同一原生任务必须通过以下端到端场景：

1. 电脑端打开任务后，手机可看到相同历史并发送一条消息；电脑端立即显示同一条用户消息且不出现活动写入者错误。
2. 电脑端发送或继续输入后，手机能收到请求、可见思考摘要、工具状态和回复增量；任务结束后与持久历史一致。
3. 手机可完成模型切换、提问回答和审批，电脑端显示相同状态变化。
4. 手机断线、PC 锁屏或原生窗口关闭时不误投输入；恢复后仍定位到原任务，未提交草稿保持不变。
5. Batona 运行期间只存在 Codex Desktop 的任务写入者；Batona 的只读 `app-server` 不加载该任务为写入状态。

## 2026-09-22 探索证据

在 Codex Desktop `26.915.4065.0` 的原生任务“运行测试”上，使用 [只读探针](../../product/pc/tools/native-codex-probe/)完成了以下验证：

- UI Automation 可按精确任务标题打开侧栏任务，并以活动 `Document` 的标题二次确认当前任务；可通过 `ValuePattern` 写入“随心输入”，再以 `InvokePattern` 调用“发送”。消息由原生界面提交，未出现活动写入者冲突。
- 手机代理输入后的用户消息和最终回复均能由只读 app-server 历史读回，内容与原生界面一致。探针没有调用 `thread/resume` 或任何写接口。
- 原生界面的回复区在生成期间暴露连续的语义文本变化。归一化探针过滤“回复已开始/回复已完成”的无障碍播报节点后，得到 `turn-start → append → complete`；八行测试正文形成 5 次单调追加，最终文本与 app-server 持久历史逐字一致。
- 模型菜单可通过 `ExpandCollapsePattern`、`InvokePattern` 和模型 `RadioButton` 操作。`GPT-5.6 Sol → GPT-5.6 Terra → GPT-5.6 Sol` 的切换均由界面状态确认，最终恢复为 `GPT-5.6 Sol / 高`。
- Codex 的 React 界面会在提交时替换 transcript 容器，并会虚拟化较早消息，因此不能缓存控件引用或用当前可见消息数量充当轮次 ID。探针按固定间隔重新取得语义容器，并以“上一轮已完成后出现新的流式正文”建立本地轮次。

这些结果证明路线可行，但还不是生产验收。当前任务标题在侧栏中唯一；生产实现必须把 app-server `thread id` 与原生任务建立更强的身份映射，并在标题重复时拒绝写入。审批、提问、工具状态、窗口关闭、锁屏、安全桌面和 Codex 升级后的选择器自检仍待逐项验证。界面代理只能转发原生界面实际显示的思考摘要，不能也不应尝试获取未显示的隐藏推理。

## 2026-09-23 任务身份绑定探针

[绑定探针](../../product/pc/tools/native-codex-probe/)现在以 `thread id` 读取该任务的标题与最近一轮完整历史，遍历只读 `thread/list` 确认标题唯一，再用 UI Automation 核对活动窗口、唯一侧栏条目、最近用户消息和助手回复。原生进程只输出文本 SHA-256 指纹，不输出会话正文。现场测试中，窗口显示其他任务时拒绝绑定；重新打开“运行测试”后，指定 `thread id` 绑定成功。单元测试覆盖同名、未列出、历史不完整、内容不符和未完成回复。

这是发送前的身份确认依据，不是长期授权。真正写入时还须在同一原生操作内重新校验窗口和任务身份，并处理 UI 切换的竞态。无法核对完整历史的任务保持只读，手机草稿保留。

## 2026-09-23 文本发送接入

PC 桥现按只读 `thread/read` 的 `originator` 区分 Desktop 原生任务与 Batona 自建任务。原生任务的文本请求走签名和包身份校验后的 Windows UI Automation 通道；独立 app-server 仅用于任务列表、标题和最新完整轮次的只读绑定。发送进程在同一操作内确认交互桌面、进程会话、窗口句柄、唯一侧栏标题、最近用户/助手内容指纹及助手完成状态，在填入草稿后、按下“发送”前再次核对。已有不同草稿、任务切换或控件不匹配均拒绝提交；Android 在错误时保留输入。

“运行测试”现场验证了原生窗口提交与 PC 桥提交，最终消息均能由只读历史读回，且未出现第二写入者冲突。故意提供错误指纹时拒绝发送，原生输入框与历史未出现测试消息。权限菜单的“请求批准”已通过窗口操作验证；切换到“完全访问”会出现原生确认弹窗，远程通道不代替用户确认。当前测试任务停留在“请求批准”档。

这一阶段只覆盖已完成轮次、唯一标题任务的文本发送。Desktop 原生任务的取消、改名、归档和审批/提问尚未接入窗口代理，会明确拒绝，不能退回第二个 app-server 写入。运行中增量镜像、可见远程控制提示及多设备租约仍待实现，不能据此宣称完整验收。签名、UI 选择器与 Codex 版本变化需要持续回归。

## 2026-09-23 模型、权限与延迟回归

PC 桥现从 `model/list` 的结构化 `supportedReasoningEfforts` 读取真实思考强度。手机选择模型或思考强度后，原生窗口代理操作模型按钮、模型单选项及强度菜单，并确认界面状态；“运行测试”现场从 `gpt-5.6-sol / high` 切到 `xhigh` 再恢复 `high`，只读 `thread/read` 与最终状态一致。手机权限弹窗同步请求原生权限菜单开合，选择后以原生界面确认的档位为准。权限若触发原生确认，远程端不代按确认。

原生发送将只读身份预期与窗口内复核合并为一次 UI Automation 进程操作，并缓存已验证的 Codex 进程 ID（操作时仍重新验证包、签名归属、会话及窗口）。同一测试任务上的本地暖态发送从约 12 秒降至约 3.6 秒，含只读绑定约 0.46 秒、原生界面操作约 3.17 秒；这不是公网手机端到端延迟。运行中增量、审批与提问仍未完成，因此双向完整同步尚未验收。

## 后果

2026-09-23 生产链路验证：Batona Gateway 0.3.1、PC 0.5.4 与 Android 0.3.3 手测 AVD 在既有配对下访问同一原生“运行测试”任务；手机提交的文本及助手回复由只读历史核对。模型、强度与权限在手机触发后由原生窗口确认，最后恢复 GPT-5.6 Sol／高／请求批准。首次冷态模型操作暴露出菜单尚未渲染就查找选择项的时序问题；PC 控件代理增加阶段码和菜单等待后，新进程手机复测通过。运行中增量及审批/提问仍未达到本 ADR 的完整验收条件。

- 手机可继续使用 Batona，同时保留 Codex 原生应用的登录态、工具、权限和任务上下文。
- 第一版需要 Windows UI Automation 事件采集、控件操作、任务身份校验和版本适配；工作量高于协议级桥接，但服务器资源远低于持续视频转发。
- 持久历史与运行期界面事件来自两个读模型，必须按任务、轮次和内容指纹去重，并以持久历史作为最终状态。
- Codex 原生界面升级可能改变可访问性控件。PC 必须按版本执行启动自检；选择器不匹配时降级为只读，不能盲目点击或伪装发送成功。
