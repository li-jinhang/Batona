# ADR 0003：以原生 Codex 窗口作为同一任务的唯一写入面

状态：已接受（2026-09-22）

## 背景

用户需要继续使用 Windows 上的 Codex 原生应用，并从 Batona Android 操作同一任务。ChatGPT/Codex 官方手机端不能替代 Batona。当前 Batona PC 另起一个 stdio `app-server`：它可以只读发现原生任务，但对原生应用已经加载的任务调用 `thread/resume` 会触发活动写入者冲突。复制、分叉或轮流抢占任务都会破坏“手机发送等同于电脑端发送”和双向实时同步。

Codex 的公开协议允许客户端连接自己启动的 `app-server`，但没有公开接口让 Batona 加入 Codex Desktop 已经持有的私有 stdio 连接。系统必须在这个边界内保持单一任务权威源。

## 决定

Windows Codex 原生应用是原生任务的唯一运行时所有者和写入面。Batona 不再通过第二个 `app-server` 向这类任务调用 `thread/resume`、`turn/start`、`turn/steer`、`turn/interrupt` 或交互响应接口。

Batona PC 增加“原生界面代理”通道。历史记录继续由只读 `app-server` 提供；任务运行期间，PC 通过 Windows UI Automation 观察经过验证的 Codex 原生窗口，把新请求、可见的思考摘要、流式回复、工具状态、审批和提问归一化为增量事件后转发给手机。任务结束后再用 `thread/read` 或 `thread/turns/list` 的持久记录校正临时增量。

手机提交消息、切换模型或处理交互时，PC 通过可访问性控件定位并操作原生 Codex 界面。实际提交动作发生在原生 Codex 输入框；模型选择、审批和提问同样由原生界面完成，因此桌面与手机操作属于同一个任务、同一个写入者。坐标点击和持续视频流不作为正常路径；只有控件无法结构化表达时，才可按需返回受限的窗口局部快照辅助用户确认。

独立 `app-server` 保留为只读镜像，用于任务列表、状态和持久历史读取。它不得把“可读取”解释为“可写入”。Batona Android 用结构化历史和增量事件维持手机聊天界面，无需持续传输桌面视频。官方协议将来若提供 Desktop 共享控制端点，可用它替换原生界面代理而不改变手机侧的任务身份。

原生窗口控制遵循以下边界：

- 仅允许配对设备控制已验证签名、包身份、进程和窗口句柄的 Codex 控件，不提供任意桌面或其他应用控制。
- 增量事件与输入经现有认证和加密链路转发；服务器不持久化可访问性树、窗口快照、按键、剪贴板或任务正文。
- PC 锁屏、UAC 安全桌面、Codex 窗口缺失、任务身份无法确认或控制链路断开时拒绝输入；手机保留草稿并显示明确状态。
- PC 显示远程控制正在进行的本地提示；同一时刻只允许一个已配对手机控制输入，电脑本地输入始终可接管。
- ChatGPT/Codex 官方手机端不属于产品依赖，也不作为 Batona 的回退路径。

## 验收

同一原生任务必须通过以下端到端场景：

1. 电脑端打开任务后，手机可看到相同历史并发送一条消息；电脑端立即显示同一条用户消息且不出现活动写入者错误。
2. 电脑端发送或继续输入后，手机能收到请求、可见思考摘要、工具状态和回复增量；任务结束后与持久历史一致。
3. 手机可完成模型切换、提问回答和审批，电脑端显示相同状态变化。
4. 手机断线、PC 锁屏或原生窗口关闭时不误投输入；恢复后仍定位到原任务，未提交草稿保持不变。
5. Batona 运行期间只存在 Codex Desktop 的任务写入者；Batona 的只读 `app-server` 不加载该任务为写入状态。

## 2026-09-22 探索证据

在 Codex Desktop `26.915.4065.0` 的原生任务“运行测试”上，使用 [只读探针](../../product/pc/tools/native-codex-probe/)完成了以下验证：

- UI Automation 可按精确任务标题打开侧栏任务，并以活动 `Document` 的标题二次确认当前任务；可通过 `ValuePattern` 写入“随心输入”，再以 `InvokePattern` 调用“发送”。消息由原生界面提交，未出现活动写入者冲突。
- 手机代理输入后的用户消息和最终回复均能由只读 app-server 历史读回，内容与原生界面一致。探针没有调用 `thread/resume` 或任何写接口。
- 原生界面的回复区在生成期间暴露连续的语义文本变化。归一化探针过滤“回复已开始/回复已完成”的无障碍播报节点后，得到 `turn-start → append → complete`；八行测试正文形成 5 次单调追加，最终文本与 app-server 持久历史逐字一致。
- 模型菜单可通过 `ExpandCollapsePattern`、`InvokePattern` 和模型 `RadioButton` 操作。`GPT-5.6 Sol → GPT-5.6 Terra → GPT-5.6 Sol` 的切换均由界面状态确认，最终恢复为 `GPT-5.6 Sol / 高`。
- Codex 的 React 界面会在提交时替换 transcript 容器，并会虚拟化较早消息，因此不能缓存控件引用或用当前可见消息数量充当轮次 ID。探针按固定间隔重新取得语义容器，并以“上一轮已完成后出现新的流式正文”建立本地轮次。

这些结果证明路线可行，但还不是生产验收。当前任务标题在侧栏中唯一；生产实现必须把 app-server `thread id` 与原生任务建立更强的身份映射，并在标题重复时拒绝写入。审批、提问、工具状态、窗口关闭、锁屏、安全桌面和 Codex 升级后的选择器自检仍待逐项验证。界面代理只能转发原生界面实际显示的思考摘要，不能也不应尝试获取未显示的隐藏推理。

## 2026-09-23 任务身份绑定探针

[绑定探针](../../product/pc/tools/native-codex-probe/)现在以 `thread id` 读取该任务的标题与最近一轮完整历史，遍历只读 `thread/list` 确认标题唯一，再用 UI Automation 核对活动窗口、唯一侧栏条目、最近用户消息和助手回复。原生进程只输出文本 SHA-256 指纹，不输出会话正文。现场测试中，窗口显示其他任务时拒绝绑定；重新打开“运行测试”后，指定 `thread id` 绑定成功。单元测试覆盖同名、未列出、历史不完整、内容不符和未完成回复。

这是发送前的身份确认依据，不是长期授权。真正写入时还须在同一原生操作内重新校验窗口和任务身份，并处理 UI 切换的竞态。无法核对完整历史的任务保持只读，手机草稿保留。

## 2026-09-23 文本发送接入

PC 桥现按只读 `thread/read` 的 `originator` 区分 Desktop 原生任务与 Batona 自建任务。原生任务的文本请求走签名和包身份校验后的 Windows UI Automation 通道；独立 app-server 仅用于任务列表、标题和最新完整轮次的只读绑定。发送进程在同一操作内确认交互桌面、进程会话、窗口句柄、唯一侧栏标题、最近用户/助手内容指纹及助手完成状态，在填入草稿后、按下“发送”前再次核对。已有不同草稿、任务切换或控件不匹配均拒绝提交；Android 在错误时保留输入。

“运行测试”现场验证了原生窗口提交与 PC 桥提交，最终消息均能由只读历史读回，且未出现第二写入者冲突。故意提供错误指纹时拒绝发送，原生输入框与历史未出现测试消息。权限菜单的“请求批准”已通过窗口操作验证；切换到“完全访问”会出现原生确认弹窗，远程通道不代替用户确认。当前测试任务停留在“请求批准”档。

这一阶段只覆盖已完成轮次、唯一标题任务的文本发送。Desktop 原生任务的取消、改名、归档和审批/提问尚未接入窗口代理，会明确拒绝，不能退回第二个 app-server 写入。运行中增量镜像、可见远程控制提示及多设备租约仍待实现，不能据此宣称完整验收。签名、UI 选择器与 Codex 版本变化需要持续回归。

## 2026-09-23 模型、权限与延迟回归

PC 桥现从 `model/list` 的结构化 `supportedReasoningEfforts` 读取真实思考强度。手机选择模型或思考强度后，原生窗口代理操作模型按钮、模型单选项及强度菜单，并确认界面状态；“运行测试”现场从 `gpt-5.6-sol / high` 切到 `xhigh` 再恢复 `high`，只读 `thread/read` 与最终状态一致。手机权限弹窗同步请求原生权限菜单开合，选择后以原生界面确认的档位为准。权限若触发原生确认，远程端不代按确认。

原生发送将只读身份预期与窗口内复核合并为一次 UI Automation 进程操作，并缓存已验证的 Codex 进程 ID（操作时仍重新验证包、签名归属、会话及窗口）。同一测试任务上的本地暖态发送从约 12 秒降至约 3.6 秒，含只读绑定约 0.46 秒、原生界面操作约 3.17 秒；这不是公网手机端到端延迟。运行中增量、审批与提问仍未完成，因此双向完整同步尚未验收。

## 2026-09-23 共享 WebSocket 入口探索（未切换生产）

已安装的 Codex Desktop `26.915.4065.0` 在本地启动路径读取内部环境变量 `CODEX_APP_SERVER_WS_URL`，可选用 WebSocket app-server 代替私有 stdio 子进程；Windows 的本地 daemon 路径不可用。桌面包内的 CLI 与 Batona 可访问的 CLI 副本哈希一致。隔离实验中，同一个 WebSocket app-server 的两个客户端可以读写同一持久任务的标题，并收到彼此的 `thread/name/updated`。另用当前登录配置做只读实验，Batona 桥经共享 WebSocket 传输的健康、任务列表、模型和权限接口均通过；没有加载或写入“运行测试”任务。

随后经协调重启，原生 Desktop 进程与 Batona 只读探针同时连接到同一个回环 WebSocket app-server，桌面端没有再启动私有 stdio 子进程。在唯一的“运行测试”任务上，第二连接 `thread/resume` 约 17 毫秒完成且没有写入者冲突；第二连接 `turn/start` 约 24 毫秒被接受，流式回复和最终历史均可读，用户确认原生界面显示了消息与回复。反向从原生界面发送时，第二连接也收到了 `turn/started`、回复增量和 `turn/completed`。两轮生成耗时约 56 秒和 82 秒，并伴随网络错误／重连，不能当作桥接延迟。Batona 桥的共享模式现可在打开任务时订阅事件，但仍拒绝手机写入并忽略服务端交互请求。审批归属、模型／强度与原生输入区同步、安卓实际下行尚未验收；生产决策暂不改变。该桌面启动入口未获公开稳定性保证，实验代码与证据见 [共享传输探针](../../product/pc/tools/shared-transport-probe/README.md)。

## 2026-09-23 共享审批与桥接实验（仍未发布）

在同一回环 app-server 的隔离临时任务上，发起端与旁观端同时收到命令审批请求，且请求 ID 均为 `122`；发起端拒绝后，两端都收到同 ID 的 `serverRequest/resolved`。临时任务已归档。这表明审批事件是广播给订阅连接的，不能假定仅发送方持有交互；`serverRequest/resolved` 只说明请求已处理，不包含处理结果。PC 桥的实验开关现在将可识别的审批/提问镜像给手机，网关把解决事件映射到手机请求编号以关闭过期弹窗；两端先到的有效答复生效。

对已加载的“运行测试”任务，第二连接单独调用 `thread/resume` 并覆盖模型后，服务端回读仍是原模型；它不能实现立即切换。通过 `turn/start` 指定思考强度则约 61 毫秒后发出 `thread/settings/updated`，服务端回读从 `high` 变为 `xhigh`；完成后又用一个回合恢复 `high`。原生输入区是否同步显示该变化仍需人工确认。该任务模式不支持提问工具，因此提问请求的真实双端体验尚未测到。

在显式 `BATONA_SHARED_CODEX_WRITES=1` 的本机桥实例上，向指定原生任务走 Batona HTTP `/prompt`，约 159 毫秒受理，约 4.2 秒内经桥的事件 WebSocket 收到回合流和完成，持久历史显示预期回复。测试中发现 `item/started` 与 `item/completed` 对用户消息和最终回复重复映射，桥已改为各发送一次。该开关默认关闭；现有安装版未更新，模型/权限切换仍保持关闭，尚未完成真实 Android→网关→PC 的共享链路验收。不能把协议可行性等同于整套功能可发布。

共享启动状态记录的桌面 PID 仅作诊断，连接取决于回环 WebSocket 地址。为避免普通快捷方式重开后失去进程环境变量，实验启动脚本现可在关闭 Desktop 后复用经进程身份、监听端口和 `/readyz` 验证的服务，再启动 Desktop 并等待实际 TCP 连接；`-Status` 可只读显示结果。用户随后完整退出并用 `-Launch` 重开，监听进程仍为 PID `26284`，新 Desktop PID `40808` 已连接。Batona 桥再次只读接入后通过健康、任务、模型、权限、写入禁用及指定原生任务订阅检查；显式本机桥实验又在约 278 毫秒受理测试文本，约 8.1 秒收到完整回复并从持久历史核对。此证据只覆盖当前 Codex 版本的共享重启与本地桥，不代表手机全链路或原生输入区显示已验收。

## 2026-09-23 手机体验回归与直接切换边界

现场检查发现运行中的 Batona PC 0.5.5 仍启动独立 stdio `codex.exe`，并没有连接 Desktop 已使用的 `127.0.0.1:45678` 共享服务。因此手机当前的设置修改仍走原生窗口菜单，Desktop 回合增量不会经 Batona 桥推送。Android 0.3.5 修正了切模型时意外回退到“中”、发送后消息显示延迟，以及没有推送时须重进会话才看到持久回复的问题；聊天页用每 4 秒一次的历史核对作为过渡，不提供流式思考。

[官方 Codex App Server 文档](https://learn.chatgpt.com/docs/app-server)支持在 `turn/start` 指定模型、思考强度和权限策略，并在共享连接上推送回合事件。本机实验中 `thread/resume` 的模型覆盖未改变已加载任务；`turn/start` 的强度覆盖改变了后端设置。随后发现当前 CLI 的实验协议还有可独立调用的 `thread/settings/update`，见下节。共享模式的 PC 桥仍拒绝模型、强度和权限写入，直到完成原生显示、持久回读、权限确认与回退测试。

## 2026-09-23 直接设置接口与重复消息回归

Android 0.3.6 修正同一用户消息在乐观显示之后，又因历史核对与较晚回推交错而显示两次：不再仅检查聊天列表最后一行，而是保留本次本地提交与其首次回推的关联。两条精确顺序的回归测试在修改前失败、修改后通过。指定“运行测试”任务的 PC 持久历史每回合只有一条用户消息；最近的同文本回合相隔数分钟或更久，不能据此判定后台重复执行。长期方案应让网关转发原生 `turnId`/`itemId`，手机按身份合并乐观消息、推送与历史，避免仅用正文和时间窗口匹配。

已安装 Codex Desktop `26.915.4065.0` 的 CLI `generate-json-schema --experimental` 含 [`thread/settings/update`](https://github.com/openai/codex/blob/main/codex-rs/app-server-protocol/src/protocol/common.rs)：参数含 `model`、`effort`、`permissions`、`approvalPolicy`，作用于后续回合，并发出完整的 `thread/settings/updated`。本机原生 Desktop 包处理该通知，更新任务内的模型、思考强度和设置快照。共享服务上的隔离临时任务无需发送消息即可切换模型与权限档；暖态 RPC 约 1 毫秒，含读取校验约 155–168 毫秒。模型单独切换时强度回到了目标模型默认值；同一请求同时带模型和原强度可保留原强度。

指定原生“运行测试”任务空闲时，通过第二条共享连接调用 `thread/settings/update`：思考强度 `medium → high → medium` 的后端回读分别在约 17/14 毫秒完成；模型 `gpt-5.6-sol → gpt-5.6-terra → gpt-5.6-sol` 并固定 `medium`，约 164 毫秒内收到设置事件与回读，最终已恢复原值。没有调用 `turn/start`，也没有改动此任务原有的 `:danger-full-access`／`never` 权限。原生输入区模型/强度标签是否同步仍待用户目视验证；权限档在原生任务上的直接切换尚未实测。

可行路线是让 Batona PC 加入 Desktop 当前的同一个回环 app-server，并以 `thread/settings/update` 原子更新模型与强度，或以已校验的内建 `permissions` 档加对应 `approvalPolicy` 更新权限；再把 `thread/settings/updated` 当作两端设置的权威事件广播。高权限档须在手机端显式确认，且要求后端回读、原生界面显示、并发修改顺序和失败回滚一致。该接口标记为 experimental，升级后须重新生成 schema 并做兼容自检；普通快捷方式启动的 Desktop 或当前未接入共享服务的 Batona PC 都不能直接使用这条链路。

## 2026-09-23 直接设置第一阶段实现

PC 源码 0.5.6 在共享 WebSocket 且本机显式 `BATONA_SHARED_CODEX_WRITES=1` 时，允许 Desktop 原生任务调用 `thread/settings/update`：切模型必须把模型 ID 与已同步的思考强度放在同一请求，并等待匹配的 `thread/settings/updated` 通知；切权限只接受 PC 的 `permissionProfile/list` 标记可用的三个固定档，并原子提交档位 ID 与对应审批策略。连接断开、并发操作或三秒内无匹配通知会返回失败，不提前把手机状态标为成功。未共享时继续使用原生窗口代理；共享写入默认关闭。

PC 只把原生设置通知投影为 `session/settings`（模型、强度、可映射档位 ID），不广播完整 `threadSettings`。网关更新内存中的会话模型快照并转发此事件；Android 0.3.7 更新当前聊天的模型/强度与权限显示，未知档位会清除旧状态。手机切换“完全访问”前增加二次确认。网关没有增加 RPC，但更新了事件联合类型与内存快照处理，因此源码候选版本升为 0.3.3，生产仍为 0.3.2。

本阶段已改源码与 Android 版本号，尚未在运行中的 Batona PC 共享桥执行端到端操作，也未目视确认原生 Desktop 标签或在 Desktop 持有任务上实际切换权限。共享协议升级兼容、并发桌面操作冲突与应用包更新后再按指定“运行测试”任务逐项验收；在此之前不把共享模式称为已发布或完整验证。

## 后果

2026-09-23 生产链路验证：Batona Gateway 0.3.1、PC 0.5.4 与 Android 0.3.3 手测 AVD 在既有配对下访问同一原生“运行测试”任务；手机提交的文本及助手回复由只读历史核对。模型、强度与权限在手机触发后由原生窗口确认，最后恢复 GPT-5.6 Sol／高／请求批准。首次冷态模型操作暴露出菜单尚未渲染就查找选择项的时序问题；PC 控件代理增加阶段码和菜单等待后，新进程手机复测通过。运行中增量及审批/提问仍未达到本 ADR 的完整验收条件。

- 手机可继续使用 Batona，同时保留 Codex 原生应用的登录态、工具、权限和任务上下文。
- 第一版需要 Windows UI Automation 事件采集、控件操作、任务身份校验和版本适配；工作量高于协议级桥接，但服务器资源远低于持续视频转发。
- 持久历史与运行期界面事件来自两个读模型，必须按任务、轮次和内容指纹去重，并以持久历史作为最终状态。
- Codex 原生界面升级可能改变可访问性控件。PC 必须按版本执行启动自检；选择器不匹配时降级为只读，不能盲目点击或伪装发送成功。

## 2026-09-25 共享权限与原生标签同步

现场反馈：手机选择任一权限档后显示成功，Codex Desktop 同一任务的权限标签不变，切走再返回仍不刷新；这是用户目视反馈，代理没有使用 Computer Use 直接观察该窗口。对共享 app-server 的低权限档实测，`thread/settings/update` 在约 70 毫秒内改变 `thread/resume` 返回的档位与审批策略，`thread/settings/updated` 也发给第二连接；这只证明后台配置改变，不能证明 Desktop 输入区标签同步。此前根据安装包中的 `latestThreadSettings`／`currentPermissions` 字段提出“权限控件未跟随外部设置事件更新”的假设，但未保存可复核的源码位置或运行时跟踪；当前安装版也未找到这两个原样标识。因此具体内部原因尚未证实，不能把该假设当作事实。真实工具调用权限尚未由用户验证。

PC 0.5.14 在共享模式改为通过已绑定任务的原生权限控件选择档位，并从共享服务 `thread/resume` 回读档位和审批策略；两者匹配才对手机报告成功。模型/强度仍走快速设置 RPC。手机 0.3.9 的完全访问二次确认通过网关 0.3.5 传递 `confirmed:true`，PC 缺少该标记时拒绝完全访问，原生控件仅在已确认时处理 Codex 自身的确认窗。旧网关若未更新会丢失标记，故发布必须先更新网关，再更新 PC 与手机；无需确认标记的低权限档兼容旧网关。原生控件绑定要求唯一标题、已完成历史、可交互窗口，无法核实时应报错，不得只改后台并把手机标为成功。

## 2026-09-25 共享权限任务绑定修正

PC 0.5.14 现场手机切权限返回“无法确认电脑端当前 Codex 任务”。对目标“运行测试”的只读共享 app-server 检查确认 `thread/read` ID、任务列表唯一标题和末轮用户/助手记录均存在；阻塞位于其后的原生窗口强历史指纹校验。权限选择是设置动作，不提交消息；PC 0.5.15 因此只对该操作使用 app-server 唯一标题与已验证 Codex 窗口的当前活动任务标题进行绑定，拒绝目标未打开或标题不唯一。发送消息、模型等既有操作继续保持末轮内容指纹和发送前复核。权限控件显示仍须与共享服务回读的档位/审批策略一致才报告成功。目标任务的只读标题绑定和模拟的缺失历史回归已通过；真实手机操作需发布后再次确认。

随后手机实测权限标签已变更，但约一秒后仍报告失败。对同一“运行测试”任务，只读调用运行中 PC 桥的权限菜单得到空档位；新建共享 app-server 连接的 `thread/resume` 则读到 `:danger-full-access`／`never`。PC 0.5.16 在持久连接回读为空或与目标不符时，用新连接再次核对；窗口设置与后台目标策略都成立才返回成功。权限设置的任务标题不匹配仅可能在触碰控件前发生，因此允许一次短暂延迟重试，其他写入不因此重试。Android 0.3.10 将权限操作的不确定结果表述为“刷新核对权限”，避免显示消息草稿文案。回归测试覆盖空回读和标题短暂不匹配；真实手机再次切换仍需验收。

## 2026-09-25 后台权限执行验证与共享切换调整

用户明确接受 Desktop 权限标签可能滞后，要求后台权限能实际决定执行。此前“标签未更新”只来自用户目视反馈，不能推出后台权限无效。为验证执行效果，在共享 app-server 上创建独立临时任务，以工作区写入沙箱和 `never` 审批策略请求下一轮写入工作区外的唯一测试文件：回合完成，文件未出现。随后对同一任务调用 `thread/settings/update` 设置 `:danger-full-access`／`never`，以相同请求运行下一轮：回合完成且文件出现。测试清理了文件并归档临时任务。另对临时任务请求 `:workspace`／`untrusted` 与 `:workspace`／`on-request`，两组后台设置调用均被接受。这个实验支持“后台设置影响后续回合执行”，但没有验证 Desktop 持有任务在下一轮是否会以输入区旧标签覆盖后台设置；此点需要手机与 Desktop 同一任务现场验收。

PC 0.5.17 因此在已显式启用的共享连接中，按目标 `threadId` 直接以单次设置请求提交固定权限档及审批策略。成功条件是匹配的设置事件，或 `thread/resume` 回读；持久连接回读空值/旧值时再用新连接核对。此路径不要求 Desktop 正显示目标任务，也不操作原生权限控件。选择“完全访问”仍须 Android 二次确认并由网关传递 `confirmed:true`；PC 在缺少标记时拒绝写入。未共享模式仍使用受身份绑定的原生窗口控制。Desktop 标签若落后，只把它视作显示状态，不再据此否定已确认的后台策略。

对本机已安装的 Codex Desktop `26.917.9434.0` 包做只读代码检查：`app/resources/app.asar` 的 `.vite/build/main-BR_2NHW6.js` 在收到 `thread/settings/updated` 时调用 `O_e`，将通知的 `threadSettings` 写入该任务的 `latestThreadSettings`。同包的 `Vxe` 准备 Desktop 的 `turn/start` 时，从这份最新设置读取 `approvalPolicy` 和 `activePermissionProfile.id`，并放入回合请求。由此推断，Desktop 下一轮通常会沿用外部设置，而非仅靠输入区旧标签决定执行权限；这是基于当前安装包的代码推断，仍须用 Desktop 自己发起的工具回合验证。该包同时保留 `currentPermissions` 等界面状态，标签滞后的具体渲染原因仍未证实。
