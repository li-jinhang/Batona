# ADR 0002：统一托管的邀请制账号与可扩展设备归属

状态：已记录 Q1–Q31（2026-09-22），Q7 由 Q11 解决，Q22 取代 Q15 中保留原账号登记的约定；产品规则已收敛，等待用户最终确认，未授权开始实现或上线。

## 决定与理由

首轮面向其他用户开放时，统一使用运营者提供的服务器，用户不自行部署。采用邀请制内测，不开放自主注册。运营者通过仅自己可访问的网页管理后台新增测试账号、查看状态、禁用账号和重置登录凭据，而非手工维护导入文件。测试账号不设到期时间，直至运营者手动禁用。此范围优先降低用户安装门槛，并让账号发放保持可控。

后台每个账号提供可修改的备注，便于运营者识别密钥发放对象；备注不参与登录。禁用不可恢复，不提供重新启用原账号的操作；用户若需再次使用，运营者生成新账号，不将禁用理解为临时暂停。

首版每位用户仅使用一台电脑、一部手机，可更换或重新绑定。单用户多电脑、多手机是明确的后续需求；账号须独立于设备存在，单台数量限制应作为首版规则，而非不可扩展的一对一身份结构。不同用户各自的电脑仍需同时在线，不能把“每人一台”解释为“全服务只有一台”。

首次接入采用“电脑登录测试账号 → 手机扫码或输入配对码 → 电脑确认 → 手机直接使用”。不要求手机再输入账号密码；以电脑明确确认手机授权代替两端分别登录。二维码只承载临时配对凭证，不承载管理员密码或服务器共享密钥。配对凭证在配对页面保持打开且电脑连接有效时有效，关闭页面、成功配对、电脑断线或程序退出后作废；恢复后生成新码，手机重新发起，不采用固定五分钟到期方案。仅最小化窗口不视为关闭页面。此断线规则仅针对未完成的配对，不撤销已绑定手机。

电脑端新增设备管理。首版已绑定手机时，不自动替换：用户必须先在电脑端解除旧手机绑定，再配对新手机。页面显示已绑定手机的名称、在线状态和最近连接时间，支持改名及解绑；本阶段不增加远程解除其他电脑登录的界面。Android 已移除的设备管理导航不因此恢复。

首版换电脑：新电脑登录后提示是否替换原电脑，经确认后原电脑断开，手机需要重新与新电脑配对，不要求旧电脑在线确认，也不要求运营者逐次人工处理。此替换行为是首版单电脑数量限制下的规则；必须保留未来同账号多电脑同时登录、独立连接及授权的扩展空间。

电脑只输入一串账号专属访问密钥即可登录，不另填用户名或密码。首版每个测试账号只有一把有效密钥。用户明确“密钥即账号”：重置密钥意味着创建新账号，不延续原账号身份。此决定取代先前未接受的“临时密码＋首次改密”建议，也不改变账号与设备分离、预留多设备归属的要求。

初期后台维护可查看完整测试账号访问密钥的密钥库，运营者拥有生成、重置和删除权限；不采用“完整密钥只显示一次”的方案。重置时旧密钥及已有设备授权全部失效，清除旧账号登记、设备登记及请求统计，创建新账号：电脑用新密钥登录，手机重新配对。Q22 明确取代 Q15 中保留原账号与设备登记记录的约定。删除密钥则同时删除账号及其服务器端设备登记，不采用“只删除凭据而保留账号”的方案。可回显完整密钥意味着不能仅存单向摘要，后续实现方案须明确可恢复密钥的存储保护、查看授权及脱敏边界，不能把完整密钥写进源码、日志或公共页面。

正常关闭、重启或短暂断网后，电脑保持登录、手机保持已完成的配对，自动恢复连接；不要求每次输入密钥或重新扫码。主动退出登录保留设备绑定登记，不释放名额，必须另外解绑才释放；保留绑定不等于保留退出端的有效登录。同一部手机主动退出后，可重新扫码或输入配对码，经电脑确认恢复原设备授权，无须先解绑；另一部手机仍须先解除旧手机绑定。电脑主动退出期间手机不能远程使用，同一电脑使用原密钥重新登录后，未主动退出的原手机自动恢复连接，无须再次扫码。此恢复规则不适用于更换电脑、重置密钥或禁用账号；解绑或重置后按新认证流程接入，禁用的账号不能再次认证。

服务器管理后台使用独立的管理员密钥，不采用本轮先前建议的“管理员账号＋密码＋动态码”。管理员凭据与测试账号访问密钥、Android 配对凭证是不同权限域；管理员密钥仅用于服务器管理后台，不能混入 PC 或 Android 的登录流程。

禁用账号、解绑或重置密钥只撤销相应远程访问，不取消用户电脑上正在执行的 DSH/Codex 本地任务；删除服务器账号及设备记录也不代表删除电脑文件或本地会话。

管理后台不提供用户工作区、会话或对话正文查看能力，只管理账号、密钥、设备、连接状态和必要操作记录。唯一使用量指标为每账号滚动近 24 小时发送请求数，各后端合并为一个数，不扩展其他统计，优先节约服务器资源。只计算手机经 Batona 成功提交给电脑 Agent 的自然语言请求，成功提交即计一次，无须等任务执行完成；提交失败、电脑原生界面请求、轮询、心跳及列表刷新均不计入。窗口为查看时刻之前的 24 小时，不是当天零点至今；重置账号后旧统计不继承。

现有用户也统一迁移到新账号与配对流程，电脑重新登录、手机重新配对一次，不保留旧连接串登录入口；实施切换前需备份和验证。首版继续使用现有服务器 IP 117.72.10.87，客户端预设入口，用户无需填写地址；不以配置域名为前置条件。HTTPS 证书信任需单独处理，此选择不代表允许跳过证书校验。

## 已核查的差距（不是已完成项）

- 当前 [PC 连接串](../../product/pc/main.js) 含共享隧道密钥和网关登录信息，不能作为独立测试账号邀请。
- 当前 [隧道服务](../../product/server/gateway/src/tunnel/server.ts) 只有一个 active 连接；[会话路由](../../product/server/gateway/src/session/router.ts) 没有用户及电脑归属。多用户上线前必须补齐隔离和路由。
- 当前 [WebSocket 推送](../../product/server/gateway/src/server/ws.ts) 广播只判断连接打开，未按认证状态和归属筛选。这是静态代码核查发现，未做线上探测；在修复并验证前不能视为可开放使用。
- 当前 PC 的 [HTTPS 请求](../../product/pc/main.js) 和 [WSS 隧道](../../product/pc/tunnel/client.js) 设置 `rejectUnauthorized: false`；Android 的 [网关客户端](../../product/android/app/src/main/java/com/batona/mobile/data/GatewayClient.kt) 信任所有证书且无条件通过主机名验证。预置 IP 不解决服务器身份验证，开放前必须移除这些宽泛放行并建立可信校验；此为源码核查，未检查当前线上证书。

后续工程约束：IP 入口须有可验证的 HTTPS/WSS 服务器身份；若采用客户端内置可信证书或公钥，必须覆盖两端全部连接路径并设计信任材料轮换，不能以首次未验证连接自动下载信任材料替代可信分发。当前安装脚本的自签流程会生成新密钥，固定信任材料时不能直接沿用该行为而不处理旧客户端兼容。具体实现和测试在获得开发确认后完成，本文不宣称已部署。
